# 踩坑记录（pitfalls.md）

> 只记"踩过才知道"的：现象 / 原因 / 解法。编号只增不改；新增一条就往下接一个号。

### P1 · `.ps1` 里的中文会被 PowerShell 5.1 读成乱码
**现象**：构建脚本报语法错或找不到变量。
**原因**：无 BOM 的脚本按系统 ANSI（GBK）读，中文注释/字符串的字节被拆错。
**解法**：本仓所有 `.ps1` **一律 ASCII**，注释写英文；中文只出现在 `.md` / `.md` 引用的文档里。

### P2 · 条码夹具两码贴太近，多码读取器也只认一枚
**现象**：一张图两枚 QR，产品只报一枚；用同一张图做单测也失败。
**原因**：解码器要求相邻码之间**每侧 ≥ 4 个模块**的静区；夹具只留了 5 个模块 ⇒ 检测阶段就并成一组。
**解法**：夹具按真实观感留 ≥ 12 个模块（260 px 的码留 90 px）；README 里也向用户写明
"两枚码贴太近会漏"——这是解码库的前置条件，不是产品取舍。

### P3 · `windui` 的窗口内容在 `SignalScope` 里，懒创建的信号会随窗口一起回收
**现象**：打开某个窗→关掉→再打开，进程直接退出（`signal.rs` 报"槽位已被回收"）。
**原因**：框架给每扇窗的内容构建开一个 `SignalScope`，关窗整批回收。若某个**进程级单例**
的信号是在内容闭包里**首次创建**的，它就归那扇窗所有，关上即死；下次 `get()` 就地 panic。
**解法**：单例信号必须在**开窗之前**创建（宿主 `open_settings` 里就是 `shortcuts_ui()` /
`plugin_hk_bootstrap()` 那句的理由）；取用法一律"只取不造"。

### P4 · 中文串上做字节前缀匹配会切进字符中间
**现象**：插件处理含中文的载荷时 panic（`end byte index … is not a char boundary`）。
**原因**：`&text[..prefix.len()]` 里的长度是**字节**数；`"12:30 开会"` 在第 8 字节处正卡在「开」中间。
**解法**：一律 `text.get(..n)`，`None` 就当不匹配。单测拿中文夹具钉住。

### P5 · 解码器给的"原始字节"不等于文本
**现象**：报告里给每一枚二维码都多印两行"字节与文本不同源"。
**原因**：`getRawBytes()` 是**码字**（QR 里含纠错码），与解出来的文本本来就不是一回事。
**解法**：只在**文本读法不可靠**（替换符 / 控制字符）时才补字节事实；干净文本只印内容。

### P6 · `deploy`/构建产物"看起来成功"其实没带改动
**现象**：改了代码、构建脚本报 OK，但行为没变。
**原因**：有的脚本只搬运不编译；`exit 0` 属于包装命令而不是被包装的命令。
**解法**：判据是**产物变了**（大小/md5/行为），不是"脚本说 OK"；后台任务读 `test result:` 行
或 `${PIPESTATUS[0]}`，别信 `echo rc=$?`。

### P7 · 仓库名是复数、目录名是单数，raw 地址两个镜像写法还不一样
**现象**：清单里的下载地址 404，宿主点「下载」如实报错——但本地构建全绿，看不出哪里错了。
**原因**：四条各绊一次。① 托管平台上的仓库名是 **`RuPix-Plugins`（复数）**，本地目录仍叫
`RuPix-Plugin/`（单数），单数地址两个镜像都 404；② 两个镜像的 **owner 不同**（Gitee
`qiuzongman` / GitHub `zongmanqiu`），只换主机名会指到别人的仓或不存在的路径；③ 默认分支
要实测（插件仓 `main`，解码器仓 `master`）；④ Gitee 的 raw 是 **302 跳转**，`curl` 不加 `-L`
拿到的是跳转页不是清单。
**解法**：写死任何下载地址之前先探一次真值（`curl -sIL` 看 200，`git branch -a` 看默认分支）。
2026-11-01 实测：两镜像的 `.../plugins.json` 都 200；Gitee 侧走
`raw.giteeusercontent.com/<owner>/RuPix-Plugins/raw/main/plugins.json`，GitHub 侧走
`raw.githubusercontent.com/<owner>/RuPix-Plugins/refs/heads/main/plugins.json`（**带 `refs/heads/`**）。

### P8 · Windows 上 `Path.write_text()` 会把 LF 文件整份改成 CRLF
**现象**：脚本"读—改—写"一个 `.md`，只动了一行字，`md5sum -c` 却对不上；`.gitattributes`
明明钉了 `*.md text eol=lf`。
**原因**：`write_text()` 底层是 `open(..., 'w')`，Windows 下默认做换行翻译 `\n` → `\r\n`，
而 `read_text()` 又先把 `\r\n` 折成 `\n`——一来一回，**全文行尾都换了**，差异里没有一个字是可见的。
**解法**：改文本优先用编辑器/补丁工具（它们保住原行尾）；非要脚本改就 `read_bytes()` +
`write_bytes()` 自己控制，或 `open(..., newline="")`。**改完数 CRLF 并与改前 md5 对账**——
本轮给 README 门面表做实弹红证时顺手撞出来一次，行尾还原后 md5 才对回来。

### P9 · 改插件自己的 `README.md` 会改掉**发布包的 sha256**
**现象**：一行代码都没动，只是把 `plugins/<id>/README.md` 里的措修辞顺，重新构建后
`plugins.json` 里那枚的 `size` 与 `sha256` 双双变了；若同名资产已经传上去，远端那份与
新清单**对不上**，宿主下载后判校验失败。
**原因**：打包器 `tools/make_catalog.py` 把插件目录里的 `README.md` / `LICENSE` 一类人读文件
**一起塞进 ZIP**（`DOC_FILES`），而 `size` / `sha256` 算的是 ZIP 的字节。
**解法**：发布顺序写成死规矩——**文档定稿 → 构建 → 打 tag → 传资产 → 推清单**，反着来就得重传。
★ **同样内容重打包不再改 sha**（2026-11-01 起）：`make_catalog.py` 把 ZIP 条目时间戳钉死成
`1980-01-01`（`ZIP_FIXED_DATE`），包字节是内容的**纯函数**。钉之前实测：一次零改动的重打就把
`checkup` 从 `e4b855a6…` 变成 `85497a25…`——那意味着清单里的 sha 描述的是"哪一刻打的包"
而不是"包里有啥"，资产与清单必须同刻对齐才不失配。钉之后连打两次 sha 一致（`building.md` §3）。
★ 根 `README.md` 的「发布插件」门面表由 `tools/check_docs.py` 第 4 查对着清单判等值，
所以"清单变了、表没跟着改"这一步不会静默过去——它会红（本轮就是它先报出来的）。
